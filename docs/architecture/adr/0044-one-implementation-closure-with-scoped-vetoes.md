# ADR-0044: What a call may run below its static target has one owner per language, and its vetoes reach only what their cause may implement

- Status: Proposed, 2026-11-08
- Decision source: requested by the tech lead on 2026-11-08 after the MCP evaluation of that day, to decide "whether
  ye-ast needs a shared model of which implementation runs behind a port, used by trace, callers/impact and
  contract_consequences alike", building on ADR-0041. The owner has not decided yet. Standing owner rules that bound
  it: facts, not guesses; noise is worse than no fix; no size threshold without a measurement; fix the mechanism, never
  one repository's case; project-agnostic; deterministic; no SCHEMA bump while the MCP has no consumers.
- Related: [ADR-0013](0013-coverage-grows-only-with-evidence.md), [ADR-0029](0029-lexical-bindings-from-the-typescript-binder.md),
  [ADR-0036](0036-dependence-is-the-compile-time-binding.md), [ADR-0037](0037-host-declared-build-outputs.md),
  [ADR-0039](0039-behavior-changes-pass-a-corpus-gate.md), [ADR-0041](0041-one-call-reconciliation-for-every-family.md),
  [RFC-0013](../rfc/0013-trace-and-patterns.md), [RFC-0021](../rfc/0021-java-value-flow.md),
  [RFC-0022](../rfc/0022-contract-change-consequences.md), [RFC-0023](../rfc/0023-consequences-surfaces.md)

**In short:** the two symptoms do not share a cause, and trace already proves a single implementation: it stops before
dispatch in one case (a build-generated supertype leaves Java names unsettled) and at a repository-wide veto in the
other (any lambda anywhere vetoes every one-method interface). Contract consequences fails for a third reason: it starts
at the root of a propagated call site and has no Java reader. What the code does show is two Java writers of "which
bodies a call may run" that disagree: trace's strict one and the call-site flow's lenient one. The fact gets one owner
per language behind the existing `dispatchTargets` port, its vetoes are scoped to what their cause may implement,
dispatch stays trace's extension of ADR-0041's base, and the dependence families keep their bridges.

## Context

### The hypothesis

The lead's hypothesis (unverified): (a) `contract_consequences` in nname cites use-case calls instead of the adapter
that issues the HTTP call (`RecipientRestRepositoryAdapter.java:41-49`), and (b) trace does not follow an interface with
a single implementation (petclinic `ClinicService` → `ClinicServiceImpl`; nname `RewardPointsRepositoryPort`), while
`callers` resolves it. Both may come from a missing shared implementation-selection model.

The last two are two writers of one fact. On the nname port the call-site flow propagates through the adapter while
trace calls the same step not proven; with two implementations and `@Primary`, trace cuts while the call-site flow
selects. AGENTS.md: "One owner per fact ... a second writer is a defect."

## Decision

1. **One fact, one owner per language.** "The bodies a call of method `m` on a value whose static type is `T` may run,
   and whether that set is closed" is the `DispatchTargets` value of `ImportOrigins.dispatchTargets`
   (`src/core/ports/import-origins.port.ts`). For Java its only writer is the dispatch reading of
   `core/adapters/spring/java-dispatch-targets.ts`. The call-site method flow stops computing implementations itself
   (`dispatchIndex.implementations`, `java-method-flow.ts:28-56`) and asks that owner. A fitness test over imports holds
   it.
2. **Separate from static binding, narrowing only.** ADR-0041's base binds the call to its compile-time declaration (the
   interface method, ADR-0041 decision 4); this fact answers what runs below it. A consumer never re-binds the call:
   the bodies are alternatives below the binding (ADR-0041 decision 6). No field of any answer changes.
3. **Dispatch stays trace's extension; it does not become a shared core layer.** ADR-0041 decision 5 holds. The
   dependence families (`callers`, `impact`, `importers`, `outline`, the callers step of contract consequences) keep
   ADR-0036 dependence and impact's dispatch bridges, which hold whatever the closure, so no closure veto ever cuts
   them. The execution readers read the one fact: trace (R7), and inside the Java adapter the call-site method flow
   (RFC-0021 S2), so `workspace`, `decisions`, trace effects and contract consequences inherit it.
4. **A framework's choice narrows a closed set only.** The Spring narrowing (`@Qualifier` at the injection point,
   `@Primary`, a named `@Bean`) moves from `java-method-flow.ts:91-98` into the owner and applies after the closure is
   proven, so trace gains it (R7's "the one the framework's dispatch proves") and the call-site flow keeps it. Over an
   unknown closure no narrowing proves anything. A candidate the framework registers conditionally (a profile, a
   condition annotation) refuses the narrowing.
5. **A veto reaches only what its cause may implement.** The precedent is the aspect veto, scoped to the join points
   its pointcuts may select (6afc788d, RFC-0013 R7). For function values: a lambda or method reference may implement a
   repository functional interface `F` only when its target type may be `F` or a type below it. Java fixes that type by
   the assignment, invocation or casting context (JLS 15.27.3, 15.13.2), and a library declaration names no repository
   type, so through a library call the target reaches `F` only by inference from a type the statement states. The
   reading takes the statement that holds the function value (the outermost statement or field or variable declaration
   not inside another function value's body) and keeps the veto for `F` when any of these holds:
   - the statement writes the name of `F` or of a type below it, in any type position (a declaration, a cast, a type
     argument, a class literal, an explicit type argument);
   - the statement names a field, method, constructor, local or parameter for which some declaration of that name in
     the snapshot states a type that mentions `F` or a type below it, a type variable, or `var`;
   - the statement is a `return` or an initializer whose enclosing declaration states such a type;
   - the statement lies inside a type at or below `F` (`this` and `super` may stand for it).

   Otherwise that function value does not veto `F`. A function value whose statement the reading does not settle keeps
   the repository-wide veto. The veto over platform annotations (`java-declared-types.ts:70-80`) keeps its current
   form: a library context may target any platform interface, so this reading proves nothing there.
6. **An undeclared supertype is never guessed.** A supertype the snapshot does not declare keeps the strict reading
   `unsettled` and the call a cut. Generated Java sources enter as an ADR-0037 build-output kind (its decision 1 lists
   "generated sources" for a later kind that has measured evidence, which this ADR supplies): a directory the host
   declares outside the repository, read as data through the confined reader, never generated by ye-ast. Its files join
   the strict reading's project as declarations, so they also count for closure (a generated implementation of a port
   vetoes it like any other), and they are never call sites, entrypoints or routes. With no lockfile analogue, a fact
   that used them states the declaration unverified (ADR-0037 decision 5). Without a declaration every answer stays
   byte-identical.
7. **A propagated request is consumed where it is issued.** For a link whose call site was propagated through other
   bodies, contract consequences starts the carrier at the issuing owned call: the owned invocation whose expansion
   reaches the leaf without passing through another owned body (`RecipientRestRepositoryAdapter.java:47` above), read
   from the placed sites (`PlacedCallSiteReader`, the reader trace effects already use). The root stays in the chain as
   the entry it was reached from. The workspace fact keeps its call sites as they are.
8. **Coverage.** Java only. TypeScript types structurally, so R7 keeps its cut; another language enters with its reader
   and conformance fixtures (ADR-0013).

## Migration

Each unit is its own commit with its fixtures failing first, passes `npm run check`, and passes the corpus gate before
it reaches `main` with the expectations stated (ADR-0039).

| Unit | Change | Gate expectation |
|---|---|---|
| V0 | The call-site flow takes its candidates from the owner's hierarchy and its Spring narrowing from the owner, still ignoring closure as today | `none`; any difference is a disagreement between the two hierarchy readings, listed and explained before V3 |
| V1 | Function values veto by decision 5 | `trace:+` (the nname quote-checkout-discount query reaches the adapter); every other family `none` |
| V2 | Trace applies the framework narrowing over a proven closure (decision 4) | `trace:+` where a qualifier or `@Primary` chooses among several proven bodies; `none` if the corpus has none (M2 says which) |
| V3 | The call-site flow propagates only through a proven closure; a method no proven call reaches becomes a root, so its site stays at the issuing call | `workspace:±`, `decisions:±`, `contract-consequences:±`, `trace:±` (effects); accepted only after the M3 report is inspected |
| V4 | Generated Java sources as a declared build output (decision 6) | `none` without a declaration; `trace:+` for a manifest query that declares one (the petclinic owner route) |
| V5 | Contract consequences start a propagated link's carrier at its issuing call (decision 7) | `contract-consequences:±`: frontiers move from root lines to issuing lines |

V0 → V1 → V2 → V3 are ordered; V4 and V5 are independent of them and of each other. V3 lands after V1 so the stricter

## Conformance fixtures

Through the adapter's port, once per consumer that wires it, each failing first in its unit:

1. **A function value in a library call (V1).** `interface Port { R q(Q x); }`, one class `Impl`, and elsewhere
   `items.stream().map(i -> i.id())`: dispatch of `Port.q` answers `Impl`'s body.
2. **A function value whose statement states the port (V1).** `Port p = x -> null;`, and `register(x -> null)` with a
   repository `void register(Port p)`: `dispatch not proven`.
3. **Inference through a sibling argument (V1).** `Objects.requireNonNullElse(port, x -> null)` with a field `Port port`:
   vetoed, since the name `port` is declared with type `Port`.
4. **`var` and type variables (V1).** `var p = make(); use(p, x -> null)`: vetoed. `<T> T id(T t)` with
   `Port y = id(x -> null)`: vetoed, since the statement writes `Port`.
5. **An inherited generic member (V1).** `class Svc extends Base<Port> { void f() { Objects.requireNonNullElse(get(), x -> null); } }`
   with `T get()` in `Base<T>`: vetoed, since `get` states a type variable.
6. **`this` below the port (V1).** A function value in a default method of `interface Sub extends Port`: vetoed for
   `Port` and `Sub`.
7. **Dependence unaffected (V1 to V3).** `callers` of `Impl.q` lists the caller of `Port.q` through the dispatch bridge,
   byte-identical with and without fixture 2's function value.
8. **Framework narrowing (V2).** Two classes implement `Port`, one `@Primary`, closure proven: trace expands the primary
   and lists both as alternatives. With `@Profile` on either: no narrowing, the cut stays. With fixture 2's function
   value: no narrowing.
9. **Trace and call sites agree (V3).** A port with `Impl` and a `@Bean Port port() { return x -> ...; }`: trace cuts
   the dispatch, the call-site flow does not propagate through the port, and the request stays at `Impl`'s issuing call.
10. **Undeclared generated supertype (V4).** A controller implementing an interface the snapshot does not declare: the
    cut is unchanged. With a declared generated directory holding it: a step at the field type's method, then dispatch
    to its one implementation, and the fact states the declaration unverified.
11. **A generated member type shadows an import (V4).** The declared generated interface declares a nested
    `ClinicService`: the field type resolves to the nested type, never to the imported repository interface.
12. **The carrier starts at the issuing call (V5).** A listener calls a use case, which calls a port, whose adapter calls
    a library client and reads the response: a hypothesis on a response property locates its finding or frontier at
    the adapter's client call, with the listener's call in the chain.

## Consequences

- Trace follows a one-method port when no function value may implement it, and, with declared generated sources, a
  controller whose supertype a generator wrote.
- `workspace`, `decisions` and contract consequences no longer state a call-site target through implementations trace
  cannot prove closed; a request behind an unproven port is reported where it is issued.
- `callers` and `impact` do not change: their bridges are dependence.
- A new host declaration (generated Java sources) is a new public CLI and library input; adding it breaks no existing
  input.
- The function-value reading costs one more pass over the statements that hold function values; M1 measures it.

## Risks

- **A closure assumption that is wrong is a false step, worse than a cut.** Every clause of decision 5 is backed by the
  Java rule it cites and by a fixture (2 to 6); a statement the reading does not settle keeps the veto; V1 is accepted
  only with M1 inspected. Recommended: an independent reviewer for V1, since a missed clause is the kind of regression
  no existing test catches.
- **The stricter call-site flow loses propagation (V3).** Where a veto still holds, a root caller loses a request it
  showed before. M3 lists every such site; V3 lands after V1.
- **Generated sources go stale.** They are stated unverified in every fact that used them; nothing claims they match
  the generator's input.
- **Framework semantics.** Profiles and conditions refuse the narrowing (fixture 8); a framework variant the owner does
  not read keeps the cut.

## Not decided here

Open questions, each with the recommended answer:

1. **Should the call-site flow become strict (V3) or keep following source implementations with a diagnostic?**
   Recommended: strict, after V1 and on the inspected M3 report. A call-site target is a fact, and following an
   implementation the closure does not prove states a target the code may never reach.
2. **The surface for generated Java sources.** Recommended: a repeatable `--java-sources [<at>=]<path>` beside
   `--node-modules`, on the same commands and in the MCP registration `ye-ast init` prints, under ADR-0037's decisions 1
   to 4; always stated unverified.
3. **Should a cut name the undeclared supertype that left a name unsettled?** Recommended: yes, a new value in the
   closed set of cut details (for example `supertype outside the snapshot`), with no SCHEMA bump: the evaluation found
   cuts without a reason hard to act on.
4. **The frontier reason for a Java consumer before a Java consumer reader exists.** Recommended: decide it in
   RFC-0022/0023; `source-unreadable` describes a source ye-ast could not read, not a language it does not read yet.
5. **Dynamic-implementation APIs and test sources.** Recommended: no change now, since trace's read does not hand test
   sources to the Java readers; if a read ever does, scope that veto by source set through the runtime rule of
   `core/domain/languages/call-targets.ts`.
6. **Sources the Java parser rejects (flexible constructor bodies).** Recommended: a separate change, a grammar upgrade
   under ADR-0007; this ADR leaves the "a source that does not parse vetoes everything" rule as it is.
