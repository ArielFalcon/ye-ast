# Corpus gate: first runs on the local corpus (2026-11-08)

The first runs of `scripts/corpus-gate.ts` ([ADR-0039](../../architecture/adr/0039-behavior-changes-pass-a-corpus-gate.md))
over the full local corpus. The question: does the gate report zero differences when the engine's behavior did not
change, and what does a run cost?

## Method

- Corpus: a manifest outside the repository with 5 groups and 14 repositories. They are Angular frontends and Spring
  backends: four groups pair one frontend with one or two backends, or hold one application with both, and one group
  pairs one frontend with five services that each declare an OpenAPI document. The largest repository has about 1,200
  TypeScript and Java files.
- The manifest names the corpus and pins every commit; no application name is recorded here.
- Inputs were frozen by the rule in ADR-0039 decision 3, from git alone, by a generator kept beside the manifest. The
  set holds 98 answers per side:

  | Family | Answers |
  |---|---|
  | entrypoints | 14 |
  | impact | 13 |
  | callers | 13 |
  | importers | 13 |
  | outline | 13 |
  | trace | 13 |
  | contract consequences | 4 |
  | workspace | 5 |
  | decisions | 5 |
  | init | 5 |

- Base: local `main` at `3ea4c47e`. Candidate: `feat/corpus-regression-gate` at `36399946`, which changes no engine
  code. Expectations: `none`.
- The machine was shared with other agents (load average 18-22). Every measure is wall time as observed.

## Runs

| Run | Answers differing | Failing queries (both sides) | Wall | CPU (user + sys) | Peak RSS |
|---|---|---|---|---|---|
| 1 | 4 (false) | 5 | 579 s | 772 s | 1.41 GB |
| 2, paths fixed | 0 | 5 | 494 s | 777 s | 1.47 GB |
| 3, inputs fixed | 0 | 0 | 495 s | 776 s | 1.35 GB |

- **Run 1** reported 4 differing answers, in the workspace and decisions of two groups: absolute repository roots.
  - The engine redacts a path segment shaped like an encoded secret (`pattern-redaction.adapter.ts`, `base64-secret`).
    It only looks at runs of 40 characters or more.
  - The random scratch segment, followed by the longer side name `candidate`, formed such a run on one side only.
  - Fix: both sides now run one after the other in the same fixed directory, and kept answers are keyed by the runner.
  - A fixture that prints its path in a form no normalization recognizes now pins the fix.
- **Run 2** gave 98/98 byte-identical answers. 5 queries failed alike on both sides:
  - `init` of a single-repository group was handed an empty workspace, which the engine refuses;
  - two callers and two trace queries named a changed range that held only a package line (`unknown-symbol`).
- **Run 3** applied both fixes: `init` runs without `--workspace` when there are no members, and the range now spans
  the file's first to last changed line. The result was 98/98 identical and every query exited 0.
- Run 3 per side: base 255 s, candidate 236 s, median query 1.7 s. The slowest queries were one trace (12.7 s), two
  impacts (12.5 s and 10.0 s) and one importers (9.9 s).

## What follows

- A gate run costs about 8 minutes on this corpus with both sides computed, and about 4 when the base answers are
  kept from an earlier run of the same `main`.
- The first run showed the harness can produce a difference the engine did not. A new corpus manifest starts with one
  run whose candidate changes no engine code, which must report zero differences. The same commit on both sides proves
  nothing, because the candidate reuses the base's answers.
